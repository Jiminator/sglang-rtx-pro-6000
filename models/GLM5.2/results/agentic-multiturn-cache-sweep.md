# GLM-5.2-NVFP4 — Agentic multi-turn concurrency sweep (radix L1 vs +HiCache L2)

Single node (8× RTX PRO 6000 SM120), **80K mean ISL / 220 OSL**, 13-turn agentic conversations,
**92.0 % designed aggregate cache hit**. Pinned to `release/v0.5.15` (`lmsysorg/sglang:v0.5.15-cu130`),
stock image, no source patches. Throughput is **total (input+output) tok/s** — output tok/s is meaningless
on this shape (220-token completions against 80K prompts; it is prefill-dominant).

Workload generated by `bench_serving --dataset-name agentic`
([PR #30304](https://github.com/sgl-project/sglang/pull/30304)), defaults
`--agentic-first-turn-len 74160 --agentic-subsequent-turn-len 753 --agentic-num-turns 13
--agentic-output-len 220` → 1,039,974 tok / 13 turns = 80,000 mean ISL, 92.0 % hit. Both arms replay a
prebuilt dataset from `--dataset-path` so conversations are bit-identical; each point consumes a fresh
slice via `--agentic-offset`.

---

## 1. Headline — L2 HiCache holds the hit rate flat; radix decays

| cc | radix hit % | **+HiCache hit %** | radix tok/s | **+HiCache tok/s** | speedup |
|---:|---:|---:|---:|---:|---:|
| 1 | 93.2 | 93.2 | 3,969 | 3,982 | 1.00× |
| 2 | 78.9 | **93.2** | 2,061 | 4,785 | 2.32× |
| 4 | 84.6 | **92.5** | 3,814 | 6,754 | 1.77× |
| 8 | 72.3 | **92.2** | 3,210 | **11,413** | **3.56×** |
| 16 | 45.3 ⚠️ | **92.0** | — ⚠️ | **13,109** | see §3 |

cc 1–8: both arms completed 100 % of conversations (4/4, 4/4, 8/8, 16/16), input tokens match within
0.05 % per point. **The GPU-only radix cache decays 93 → 72 % under concurrency while L2 holds the designed
~92 % flat**, and that converts directly into throughput.

## 2. The gain is exactly the avoided re-prefill

Uncached tokens = total input × (1 − hit). Effective prefill rate = uncached ÷ duration:

| cc | radix uncached | +HiCache uncached | predicted | measured | radix prefill tok/s | +HiCache prefill tok/s |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 280,190 | 280,262 | 1.00× | 1.00× | 269 | 270 |
| 8 | 4,560,404 | 1,282,774 | 3.55× | **3.56×** | 887 | 888 |

At cc=1 and cc=8 both arms prefill at an **identical rate**. HiCache does not make the GPU faster — it does
strictly less work, in the amount the hit rate predicts. (cc=2/4 undershoot the prediction because a decode
floor dilutes the ratio at low concurrency; it washes out by cc=8.)

## 3. ⚠️ cc ≥ 16: radix does not complete — not a throughput comparison

| | radix | +HiCache |
|---|---|---|
| cc=16 conversations completed | **8 / 32** | **32 / 32** |
| cc=16 input tokens served | 8.8 M | 32.9 M |
| router errors | **1,257 × HTTP 503** @ ~360–400 s | **0** |
| backend health-check failures | 248 | 16 |

Radix cc=16's raw 2,186 tok/s is computed over a quarter of the work — **do not quote it as a 6× speedup.**
Mechanism: radix-only prefill saturation made the backend unresponsive to the router's health probe, the
router marked the worker down and 503'd requests. This is a genuine operational failure mode (low hit →
80K re-prefill → saturation → health-check timeout) but a **serving-stack** limit, not a proven pool wall;
a tuned health-check timeout would likely change it. Treat cc≥16 as qualitative.

## 4. Why this differs from the 1K/8K zipfian result (+3 %)

[`concurrency-sweep.md`](./concurrency-sweep.md) found L2 HiCache worth only ~+3 % on zipfian 1K/8K and
concluded "radix L1 is sufficient". Both are correct — **different bottlenecks**:

| | zipfian 1K/8K | agentic 80K/220 |
|---|---|---|
| Bottleneck | decode-generated KV | **prefill of re-sent prefix** |
| Prefix size | ~896 tok | **~74–86 K tok** |
| L2 benefit | ~+3 % | **up to 3.56×** |

Caching cannot dedup decode-generated KV, so on an OSL-8192 workload L2 has nothing to fix. On agentic
multi-turn the re-sent prefix *is* the cost. **"L2 HiCache is optional" is workload-specific, not general.**

## 5. ⛔ Speculative decoding — blocked on SM120 by an upstream regression (#29787)

A third arm (HiCache + EAGLE, blog flags `--speculative-num-steps 5 --speculative-num-draft-tokens 6
--speculative-eagle-topk 1`) **could not be run.** Every EAGLE config dies at draft cuda-graph capture:

```
TypeError: FlashInferMLAAttnBackend.forward_decode() got an unexpected keyword argument 'topk_indices'
```

**Root cause:** [`16372b4c5f` "[Spec] Anchor GLM-5.2 MTP IndexShare topk on the draft-extend step"
(#29787)](https://github.com/sgl-project/sglang/pull/29787), merged 2026-07-06 — after `b28bc1060`
(07-04) and before `v0.5.15` (07-09). It threads `dsa_topk_indices` through the EAGLE draft path, but
`flashinfer_mla_backend` implements no such kwarg (**0 refs** at b28bc1060, v0.5.15, post1 *and* main;
only `dsa_backend` has it, 57 refs). On SM100 the draft uses the deep_gemm-backed DSA path which accepts
it; **SM120 has no deep_gemm build**, so it falls back to `flashinfer_mla` and dies. Forcing
`--speculative-draft-attention-backend dsa` hits the other jaw: `deepgemm/csrc/apis/attention.hpp:227
Unsupported architecture`.

⇒ **IndexShare, the blog's headline spec optimization, is exactly what breaks spec decode on SM120.**

**This is a regression, not a limitation** — the same feature worked on this hardware and checkpoint
before v0.5.15: EAGLE 3-step **300 tok/s/GPU** (06-29, accept_len 3.93) and EAGLE-3 + fp8 **330 tok/s/GPU**
(07-05 on `dev-cu13` @ `b28bc1060`, accept_len 4.0). `b28bc1060` is a verified ancestor of `v0.5.15`.

Ruled out as causes: the blog env vars, HiCache, the image (v0.5.15 vs post1), and step depth (3/4 fails
identically to 5/6). Newer images cannot help — main has 0 refs too. Fix is source-only, so work stopped.

**Practical guidance:** do **not** pin `release/v0.5.15` for GLM-5.2 on SM120 if spec decode is required;
the regression is in the release. Pre-#29787 builds are known-good. On a current build, **NEXTN** still
boots (it avoids the IndexShare path) but spec buffers cut the KV pool **−68 %** (129,216 → 41,344/rank at
matched mfs), below the 90,112 context length; mfs 0.96 + chunked-prefill 8192 recovers it to 113,472,
which fits **one** conversation per rank — so a NEXTN sweep is viable only at **cc ≤ 8**.

**Would spec have helped?** Probably not for throughput. Aggregate throughput here is prefill-bound —
solving `duration = prefill_work/R + decode_time` across the two cc=8 arms yields decode_time ≈ 0, i.e.
continuous batching already hides decode behind other requests' prefill. Spec accelerates decode (already
free in aggregate) while spending the KV pool that produces the 3.56× win. It remains a **latency** lever:
decode is 39–66 % of per-request E2E. Full detail: `_raw/glm5.2/agentic_spec_bootfail/BOOT_FAILURE.md`.

## Config

```
--tp 8 --dp-size 8 --enable-dp-attention --moe-a2a-backend none --ep-size 1
--moe-runner-backend flashinfer_cutlass --attention-backend flashinfer --kv-cache-dtype fp8_e4m3
--disable-shared-experts-fusion --mem-fraction-static 0.92 --chunked-prefill-size 16384
--cuda-graph-bs 1 2 4 8 12 16 --cuda-graph-max-bs 16 --context-length 90112
--max-running-requests 128 --enable-cache-report
env: SGLANG_DISABLE_DSA_INDEXER_FUSION=1 + PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True + NCCL/GLOO block

+HiCache arm adds:
--enable-hierarchical-cache --hicache-ratio 2.0 --hicache-mem-layout layer_first
--hicache-io-backend kernel --hicache-write-policy write_through_selective
```

Resolved: pool **129,216 tok/rank** (1.03 M agg), 7.59 GB free/GPU, chunked-prefill 2048/rank, max-running
16/rank (DP-attention divides both by `dp_size`). `mem-fraction-static 0.92` is deliberately below the 1K/8K
0.975 ceiling — this workload over-subscribes the pool, where the known failure is a queued 80K prefill's
activation colliding with a full decode pool.

## ⚠️ Routing is load-bearing (else you measure 0 % hit)

Under DP-attention each rank owns a **separate KV pool and radix tree**, and no built-in DP balancer is
cache-aware (`round_robin | total_requests | total_tokens | follow_bootstrap_room`). Round-robin scatters a
conversation's turns across ranks → **`#cached-token: 0` on every request**. A 92 %-hit workload measures 0 %.

Required topology — **two processes**, not `sglang_router.launch_server` (that spawns `dp_size` independent
`tp_size`-wide replicas → 8×8 = 64 GPUs → `invalid device ordinal`):

```bash
# 1. DP-attention server on an internal port
python3 -m sglang.launch_server ... --port 30000

# 2. cache-aware, dp-aware router in front (mount the HF cache, or prefix
#    matching silently loses its tokenizer)
python3 -m sglang_router.launch_router \
  --worker-urls http://127.0.0.1:30000 --dp-aware --policy cache_aware --port 8000
```

## Measurement caveats

- **Hit rates are server-derived, not client-reported.** The client reads hits from an `sglext` SSE chunk;
  the router re-serializes chunks through a typed model with no `sglext` field, so it is dropped in transit
  and **every client-reported hit rate reads a false 0.0 %** (the `usage` chunk survives, so input-token
  accounting is fine). Rates above come from the scheduler's own `#new-token`/`#cached-token` accounting.
- **No device-vs-host split** — it rides the same dropped field. Aggregate effect is unambiguous; the
  L1/L2 tier breakdown is not measured.
- **Router in the path.** The 335 tok/s/GPU 1K/8K SOTA was measured without a router; absolute throughput
  here is not comparable to it. The radix-vs-HiCache delta is, since both arms share the router.
- `--enable-metrics` was on for the HiCache arm only (added mid-run). Counters only; noted for completeness.
- Single run per point. cc=2 radix is noisy (78.9 %, below cc=4's 84.6 %, breaking the monotonic decay).
